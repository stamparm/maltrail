# Request paths no host-less path trail may match (sensor/tools/check_trails.py --path-canaries).
#
# A trail written without a host - "/wp-admin/maint/" - fires on that path on EVERY host, and the
# sensor also looks a request up by its parent directory and its last segment
# (sensor/src/protocols/http.rs:build_checks). So "/wp-includes/id3" fired on every WordPress site
# and "/updraft" on any path ending in it. These shipped as "emotet (malware)" and "zloader
# (malware)", HIGH, and reached real alerts before they were found by hand.
#
# Three sections, each a different way an ordinary request looks like an indicator:
#   1. WordPress 7.1.4 core, every file and directory (lower-cased: the sensor lower-cases the path).
#      The CMS behind most of the web, and every CMS false positive so far was one of its paths.
#      Joomla and Drupal core were measured too and added one "web shells (suspicious)" filename.
#      Its shell.php and mysql.php are left out: those are classic web-shell names, true positives.
#   2. Standard paths of other common software: FrontPage, Dreamweaver, UpdraftPlus, and the like.
#   3. Default build-output and generic file names (Android Studio, one-letter scripts).
#
# A hit is a QUESTION, not a verdict: --allow-trail accepts a trail that really is that broad.
# Regenerate section 1 from https://wordpress.org/latest.zip when WordPress moves a directory.
