# Maltrail sensor

The Maltrail sensor: packet capture and trail detection, in Rust. Same `maltrail.conf`, same
`trails.csv`, same event format — so the Maltrail server and web interface need no changes.

This is the sensor to deploy. `sensor.py` remains in the repository as the **old sensor**: the
reference implementation, the differential-test oracle this suite replays against, and the way to
get the one feature implemented only there (the `meta.sqlite` condensed observable store).
Nothing about it was removed.

**Road to becoming Maltrail's default sensor: [`docs/ROADMAP.md`](docs/ROADMAP.md)** — gated, with
verifiable exit criteria and the open blockers stated plainly.

Needs no root: `CAP_NET_RAW` (plus `CAP_NET_ADMIN` for promiscuous mode and `PACKET_FANOUT`) is
enough, and `-T` validates a deployment before you trust it.

```bash
# build
cd sensor && cargo build --release

# run (live capture)
sudo ./sensor/target/release/maltrail-sensor

# run (offline replay)
./sensor/target/release/maltrail-sensor -r capture.pcap -c maltrail.conf --offline
```

## Status

* Differential parity against `sensor.py`: **36/36 corpus cases, 0 event differences.**
* Tests: **261** (unit + integration + shared vectors generated from the Python code +
  deterministic fuzzing of every parser).
* Live capture and `PACKET_FANOUT` verified on real hardware: 4 workers in one kernel group,
  20,000 packets **distributed** 5018/5025/5047/4910 and **not duplicated** (4-worker total
  identical to the 1-worker baseline).
* Measured offline full-sensor replay with a real 1.5M-trail set: **~13.8x lower per-packet
  cost** than `sensor.py` (1.2 µs vs 16.7 µs), **3.4x** faster end to end for a 300k-packet run
  (startup dominates a short replay). Software packet path scales to **~10 Mpps** across 16
  workers on an 8-core/16-thread laptop.
* Where `sensor.py` still wins: **startup** (0.20 s warm vs 1.18 s) and **peak RSS** (63 vs
  88 MB), because `core/trailsbin.py` mmaps a prebuilt binary trail store while the sensor
  parses the CSV on every start. Python's *cold* start, which builds that store, takes 7.63 s.
  Closing this is the top next step in `docs/REPORT.md` §7.1.

See `docs/REPORT.md` for the measurements and how to reproduce them, and
`docs/COMPATIBILITY.md` for the (short) list of deliberate differences and unimplemented
features.

## Layout

```
sensor/
  src/
    main.rs          CLI, startup, diagnostics, worker spawn, reload + metrics threads
    config.rs        maltrail.conf parser (port of read_config)
    settings.rs      compiled regexes / matchers
    settings_gen.rs  GENERATED from core/settings.py by tools/gen_settings.py
    pyre.rs          Python `re` compatibility (re.escape, \Z, literal braces, group rules)
    addr.rs          native IP type + Maltrail's exact address rendering
    smallstr.rs      fixed-capacity stack string (allocation-free rendering)
    trails/          streaming CSV loader, string + native lookup tables, wildcard regex
    whitelist.rs     WHITELIST / WHITELIST_RANGES
    packet/          DLT/VLAN offsets, offset learner, IP/TCP/UDP/ICMP
    protocols/       dns.rs http.rs tls.rs quic.rs
    heuristics/      scan.rs dns_exhaustion.rs nxdomain.rs
    process.rs       the port of _process_packet() and _check_domain()
    state.rs         per-worker state (caches, burst suppression, accumulators)
    event.rs         event tuple, safe_value(), log-line + repr rendering
    output.rs        log file, LOG_SERVER, CEF, Logstash, condensing, throttling
    ignore.rs        IGNORE_EVENTS + IGNORE_EVENTS_REGEX
    capture/         libpcap handles, PACKET_FANOUT
    worker.rs        run-to-completion capture loop
    metrics.rs       worker-local counters + lock-free aggregation
    testkit.rs       in-process harness for tests, benches and fuzz targets
  tests/             detection, replay, trails, vectors, capture_live, fuzz_parsers
  tests/corpus/      generated replay corpus (36 pcaps + fixture trails + manifest)
  tests/vectors/     test vectors generated by calling the real Python functions
  benches/hotpath.rs microbench / packet-path / replay / worker-scaling benchmarks
  fuzz/              cargo-fuzz targets
  tools/             gen_settings.py gen_vectors.py gen_corpus.py parity.py
                     update_trails.py dump_trails.py bench_compare.py fanout_check.py check.sh
                     bench_compare.py fanout_check.py check.sh
```

## Everything that must pass

```bash
sh sensor/tools/check.sh
```

which regenerates the Python-derived constants/vectors/corpus, then runs `cargo fmt --check`,
`cargo clippy -D warnings`, the full test suite, a release build and the differential parity
harness in both timestamp modes.

Separately, once per deployment (needs privileges):

```bash
sudo python3 sensor/tools/fanout_check.py --interface eth0 --workers 4
```

## Benchmarks

```bash
cargo bench --bench hotpath                                    # Rust, staged
python3 sensor/tools/bench_compare.py --slope \
        --trails ~/.maltrail/trails.csv                        # Python vs Rust, offline replay
```

Numbers are reported in three clearly separated categories — isolated microbenchmarks, full
packet path, and pcap replay — plus worker scaling, so a microbenchmark can never be mistaken
for sensor throughput.
